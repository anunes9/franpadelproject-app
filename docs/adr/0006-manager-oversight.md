# Reassigning a Class Group and removing a Coach

The parent spec (#6) lets a Club Manager reassign a Class Group to another Coach of the same Club and blocks removing a Coach while they own groups (user stories 12 and 13). It leaves open who exactly can reassign, whether a reassignment is clash-checked, what removing a Coach does to their account, and where the removal rule lives. We decided:

- **Only a Club Manager of the group's Club reassigns it**, through `ClassGroup.visible_to`. The group's own Coach, other Coaches, Managers of other Clubs and Admins get a 404, like every other screen they cannot use.
- **The new owner must be an active Coach of the group's Club.** Anyone else is refused with a code on `coach`: `blank` for a user that does not exist, `not_a_coach` for a Club Manager or an Admin, `other_club` for a Coach of another Club, `removed` for a removed Coach. The removed check is repeated under the reassignment's lock on the new Coach, which a removal takes too, so a Coach removed meanwhile is never handed the group. A group's Club is its Coach's Club, so the group and its Players never change Club.
- **The Training Plan is kept as it is.** Its Classes keep their dates, times, Modules, Exercises and done or skipped marks. Nothing is regenerated.
- **Reassigning is clash-checked for the new Coach**, as every change to who teaches a Class is. The group's upcoming Classes (dated today or later in Lisbon, `Academy.today`, neither done nor skipped, as in ADR 0004) must not overlap another Class of the new Coach. A clash refuses the reassignment with the clashing dates and changes nothing. Past and done Classes are history and never refuse it. The Players do not change, so they are not checked again.
- **A reassignment is all or nothing.** The check and the change run in one transaction holding a lock on the group itself and `ClassClash.lock` on the new Coach and the group's Players, so two reassignments of one group run one after the other.
- **Removing a Coach is a soft removal: they lose access, their data is kept.** The product owner decided to "remove his access from the platform but keep the data for historical purpose". `User#remove!` sets `users.removed_at`; the account, course progress, Exercise Completions and every other row stay as they were, and so do their Club, its Players and its Coach Invitations. A removed user cannot sign in (Devise's `active_for_authentication?`), and an open session ends on their next request; the sign-in page says the account no longer has access (`removed`), which Devise only reveals to someone who gave the right password. A removed Coach drops out of every list of the Club's Coaches, its counts and the reassignment choices (`Club#coaches` is active Coaches only, over `User.active`); the Club still cannot be deleted while it has any users, removed ones included.
- **A removed Coach's email stays taken.** Inviting it is refused as `account_exists`, as for any existing account. Reactivating a removed Coach (by an Admin, or by accepting a new invitation) is a follow-up.
- **A Coach who owns any Class Group cannot be removed**, finished groups included, so every group's Coach is an active one. The Manager reassigns the groups first. The Club overview says so next to the Coach.
- **The rule lives on the model.** `User#remove!` refuses while the user owns Class Groups (`base: has_class_groups`), so the admin Users screen, the console and any future screen are held to it too, not only the Manager's screen. It locks the user's row before checking, so a reassignment to them (which locks the new Coach) waits or is seen. A hard delete, which nothing in the app does any more, is refused the same way by a `before_destroy` guard under the same lock, with the foreign key from `class_groups.coach_id` as the database's backstop.
- **Only a Club Manager of the Coach's Club removes a Coach** from the dashboard. A Coach of another Club, a removed Coach, a Club Manager, an Admin, or the Manager themselves is a 404 there.
- **Admins remove users too, never delete them.** The admin Users screen's Remove link and batch action call the same `User#remove!`, for every role, so history is kept whoever removes the user. The screen shows each user's status and `removed_at`, and filters by status. A real delete is left to the console.

## Considered options

- **Deleting a removed Coach's groups, or leaving them ownerless**: rejected by #6. Groups survive staff changes.
- **Reassigning the groups automatically on removal**: rejected. The Manager picks each new owner, and each pick is clash-checked.
- **Deleting the Coach's account** (the first decision): replaced by the soft removal, on the product owner's request to keep the data for historical purpose. Deleting lost the Coach's course progress and Exercise Completions.
- **Keeping the Coach's account but unlinking them from the Club**: rejected. A Coach must belong to exactly one Club, so an unlinked Coach is invalid; a removed Coach keeps their Club, for history.
- **Keeping the admin delete as a guarded hard delete**: rejected. It would make Admins the one way to lose a Coach's history, and two meanings of "remove" for the same user.
- **`dependent: :restrict_with_error`**: equivalent, but its error code (`restrict_dependent_destroy.has_many`) is Rails' rather than ours, so the screens could not tell this refusal from any other. We keep the same behaviour with our own code.
- **Reassignment without a clash check**: rejected. It would double-book the new Coach, breaking the clash rule of #6.
